PART24 item 1: seed 1 run pre-emptively on separate pods
Written 2026-09-23 (UTC ~22:02). Whole-interview projector fine-tune of Qwen2.5-Omni on E-DAIC, 275 windows.

Why
The p24-ft pods run seed 0 on their fold, and only after that do they rerun seed 1, and only if the fold's
median Yes+No answer mass is below 0.5. So any seed 1 result would come at least one full fold run late.
To save time, seed 1 now runs for every fold right away, on 5 separate pods, in parallel with seed 0.

Design
1. Seed 0: pods p24-ft0..p24-ft4, fold k on p24-ft{k}, unchanged. Driver run_fold24.sh.
2. Seed 1: pods p24s1-ft0..p24s1-ft4, fold k on p24s1-ft{k}. Same GPU (NVIDIA H200), same image
   (runpod/pytorch:1.0.2-cu1281-torch280-ubuntu2404), same setup (setup.sh: model download, E-DAIC fetch, pip),
   same smoke gate (smoke24.sh), same window build and fold check, same sft_whole24.py (sha256 ad2cf8c9...),
   same env (GC=on, CK=55, 3 epochs, AdamW 1e-4, one clip per update, CE on the Yes/No logits, only
   thinker.audio_tower.proj trained). Driver run_fold24_s1.sh: run_fold24.sh with seed 0 and the mass rule removed.
   It runs ONLY seed 1 on fold k, with no mass rule.
   Outputs keep the seed 1 names the driver uses: out/FT_whole_s1_fold{k}_oof.csv, out/FT_whole_s1_fold{k}_oof.sidecar.json,
   out/FT_whole_s1_fold{k}.RESULT. The sidecar has an extra field "note": "seed 1 run pre-emptively on a separate pod,
   in parallel with seed 0, to save time; same scripts and seed rule". p_yes, answer_mass and audio_tok for every test
   clip are in the oof csv and were also printed to the pod logs.
3. The seed rule is unchanged. The reported result uses seed 1 only for folds whose seed 0 median answer mass is
   below 0.5 (the value in out/MASS_CHECK_fold{k}.txt on the p24-ft pod). For the other folds, the seed 1 result
   from the p24s1 pod is kept and labelled extra. It is not used in the reported number.
4. Where a p24-ft pod also reruns seed 1 on the pod itself (its fold's seed 0 median mass < 0.5), that fold has two
   seed 1 runs: the p24-ft run and the p24s1 run. Same script, same seed, same data, so the two are a reproducibility
   check. They are expected to agree closely. They may not be bit identical (different GPU hosts, bf16 kernels).

Shutdown
watchdog24.sh re-reads its pod list on every loop, so the 5 p24s1 lines were appended to that list (the 5 p24-ft
lines were not touched). The same watchdog pulls each p24s1 pod into a tar file plus an extracted folder
when /workspace/ALL_DONE exists, checks the file count and the result file sha256, and then deletes the pod.
On-pod backstop: guard24.sh (the PART24 guard) stops the pod if ALL_DONE is older than 30 min, or idle 40 min, or after 5 h.

Files
scripts/part24/pod/                    stage scripts, the same on every pod (sha256 checked against the pod and the stage list)
scripts/part24/pod/run_fold24_s1.sh    seed 1 driver
scripts/part24/pod/launch24_s1.sh      upload and start script
scores/part24/pods/p24s1-ft{k}/        per fold outputs pulled from each pod (after the run)
The pod create requests and responses, the upload sha lists and the launch log stay on the authors' machine.
